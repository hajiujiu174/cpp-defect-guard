# CodeGuard 四级开发路线图

当前依据新方案书 V1.0，目标为 16 周内完成 Level 3。旧“第一/二/三层”编号不再用于新版本验收。详细迁移关系见 [codeguard-migration.md](codeguard-migration.md)。

2026-09-10 用户调整：交付仅面向 Windows，跨平台工作暂缓。当前优先级以根目录 AGENTS.md 为准；Windows CI 与可复现构建见 [专项说明](windows-ci.md)。

## Level 1 必做：可运行骨架（当前）

- 已有：顶层 CMake、多目标构建；独立 C++ Core / CLI；Qt 初版；只读文件扫描、基础物理行统计、忽略目录、文件变化识别；SQLite 项目/扫描/文件历史、事务回滚、最近项目与重新打开。
- 已补齐 P1-1：编译数据库发现/生成、工程配置持久化、Qt 设置与重启恢复、多命令显式选择。范围和回归见 [配置管理](project-configuration.md)。Windows 打包、源码定位、后台扫描、取消/错误恢复和安全关闭见 [前端说明](qt-frontend.md)。后续按 AGENTS.md 推进 P1-2。
- 验收边界：Windows 既有构建测试和运行包验收见 Level 3 说明；WSL Core 已有历史通过记录，Linux 全功能与其他平台验收暂缓。

## Level 2 核心：真实工程解析与质量分析（进行中）

已交付：Core 内置 LibTooling、准确匹配编译数据库、USR 符号与定义合并、CFG 圈复杂度、直接调用图、include 依赖图、BFS/DFS/SCC/拓扑排序；SQLite schema 2 持久化；CLI 前缀检索/复杂度排行/图查询；Qt 结果与覆盖诊断标签页。旧独立分析器保留兼容。验收及边界见 [codeguard-analysis.md](codeguard-analysis.md)。

剩余优先级：

1. 扩展宏与引用索引、定义/引用跳转；补齐 lambda、间接调用及多构建配置的建模策略，不把当前直接调用图当成全运行时调用图。
2. 增加最大嵌套、扇入/扇出等度量；对不同 TU 宏上下文保留版本化溯源，当前图是成功 TU 的合并视图。
3. 提供可交互的图布局与路径查看；当前 Qt 显示关系边表和循环 SCC 成员，支持点击关系边定位源码，但不是完整图画布。
4. 已接入五类 AST 规则及 Issue 存储，保留证据、建议、解析覆盖和失败诊断；后续扩大规则评测，详见 [Level 3](level3-acceptance.md)。
5. Qt 已接入可筛选、可定位的规则问题列表；CLI 与 GUI 使用同一 Core 结果。

## Level 3 完整：课程交付目标

1. 已实现自研查询 Lexer → Parser → AST → 语义分析 → 执行计划 → 执行器；覆盖 WHERE 优先级、括号、类型检查、多字段排序与 LIMIT。CLI / Qt 共用六类快照实体查询（含 issues/builds），不把用户查询拼入 SQLite。当前内存执行、GUI 显示最多 2000 行；后续按真实规模补充性能实验与异步查询，见 [查询语言](query-language.md)。
2. 已实现有界任务队列、多 TU 线程池、单写线程批量事务；提供 1/2/4/8 线程实测脚本，结果按原始数据记录。任务独立 Clang 文件系统，支持取消、进度、异常传播与提交前回滚。
3. 已实现 Windows/POSIX ProcessRunner，参数数组、stdout/stderr、超时/取消与进程组清理；接入副本内 CMake/CTest 和受控 Git 读取。
4. 已补齐 schema 3 BuildTest/Issue 持久化、GoogleTest 合同测试、Windows 运行包脚本。Windows 与 WSL Core 有本机验收记录；新增 Windows CI 的执行结果见专项说明，Linux 全功能环境暂缓。GraphEdge 保留 schema 2 的结构。
5. 已完成课程工程及固定 cJSON、TinyXML-2、fmt 的真实工程验收，包含构建测试、覆盖、资源测量、线程一致性和全部告警复核，见 [P0-2 报告](real-project-acceptance.md)。未覆盖配置、完整缺陷真值和更大工程仍有边界，不可将 Juliet 函数分类结果替代工程管理验收。

## Level 4 增强：时间盒研究

已有 AST/CFG/局部 DFG、独立标签、Juliet 导入器和 Python 模型实验全部保留为研究资产。暂停新扩容和新训练轮次，先稳定 Level 1—3。上一轮新增池化/正则融合低层实现尚未接完训练入口与对照验收，不能当作已通过模型。

后续可选 CFG/DFG 深规则，或函数级 AI 分类/修复；部署优先 ONNX Runtime C++。扩散生成必须经过编译、静态检查和测试筛选，不承担基础缺陷检测。默认不加载模型，不要求 Python 即可运行 Core / CLI / GUI。

# 旧三层次路线（历史记录，不再作为当前排期）

## 第一层 基础交付 第1至8周

### 已完善

- Python 包、`scan`、`verify`、`doctor`、`rules` 命令和 TOML 配置校验。
- C/C++ 文件发现、工程识别、函数边界与近似 CFG。
- 七类可解释规则、注释与字符串屏蔽、严重度过滤和 CI 退出码。
- 规模、注释、重复、复杂度、嵌套、依赖和告警密度指标。
- JSON、Markdown、HTML 报告和可兼容迁移的 SQLite 记录。
- 临时副本隔离构建测试、完整日志和源码指纹保护检查。
- LLVM/Clang 22.1.8 与 CMake 4.4.3 本机接入，原生 AST/CFG 工具构建和 Python 集成。
- DG001/DG002/DG004 迁移到 AST，函数度量与原生 CFG 对齐。
- 中文路径、宏、模板、共享头文件、变量遮蔽和失败诊断测试。
- 覆盖正例、反例、结构、报告和隔离验证的自动化测试。
- 成对的缺陷版本与修复版本样例，以及一键对比脚本。

### 剩余改进

1. 将 DG003/DG005/DG006/DG007 迁移到具备路径、资源和别名语义的检测器。
2. 建立独立标注的规则评测集，统计误报与漏报，避免仅凭两组样例评价精度。
3. 扩充跨文件资源管理、宏模板变体和复杂控制流用例。

### 验收

- 样例工程一次命令完成扫描。
- 告警包含规则依据、严重度、文件、行列、证据和修复建议。
- 三种报告和 SQLite 内容一致。
- 构建与测试日志可复现，原始源码哈希不变。

## 第二层 智能增强 第9至12周

### 已实现的实验闭环

- 原生 AST/CFG/局部 DFG、调用信息、源码映射和 JSONL 导出。
- 24 个自建函数、独立二分类/行标签、来源/模板组隔离、固定种子和去重检查。
- 冻结 GraphCodeBERT 序列二分类基线、两层 RGCN 及序列—图融合。
- 训练配置、数据/编码器/权重指纹、验证集选轮次、safetensors 检查点和重载评估。
- Precision、Recall、F1、Accuracy、混淆矩阵、Top-k 和端到端 Top-k；序列基线明确不支持定位。
- 去 CFG（节点与相关边）、去 DFG（定义—使用边）消融入口。
- `models.backend=trained` 接入原生扫描、三种报告与 SQLite；默认禁用模型。
- v0.5.0 加严图结构、来源追溯与划分清单校验，拒绝重复字段、非有限值和伪造的来源隔离。
- 加载时验证编码器主干、tokenizer、检查点元数据及张量；新增带内容指纹的特征缓存。
- `doctor` 提供当前解释器的模型轻量预检，扫描报告列明未覆盖文件/函数与序列截断。
- 固定数据划分，完成三种模型各三个种子的实验；汇总均值、样本标准差和逐样例错误，支持校验后恢复。
- 新增 NIST Juliet C/C++ 1.3.1 的受控导入器：固定归档哈希、ZIP 路径安全检查、原始字节/来源保存、答案词过滤、模板/近克隆组隔离和只编译 C 叶函数对。
- 完成首批 120 个 Juliet 用例对验收：240 个原生函数图、239 条去重后样本、29 个来源组及固定的训练/验证/测试划分；细节见 `docs/juliet-import.md`。
- 修正 Juliet 局部答案命名，新增 `semantic-v2` 整数/字符常量、运算符、数组容量和绑定特征；无正例行监督时关闭定位损失。完成同批 11 次分类对照，新 GNN 验证平衡准确率均值 56.7%，融合均值 50.0%，未达到预登记扩容门槛，暂缓扩容；见 `docs/juliet-correction.md`。

### 剩余改进

1. 按许可证继续扩展 Juliet 的 C++、跨过程和更多流变体，并接入第二个来源不同的公开数据集；增加抽样人工复核。
2. 扩充验证/测试规模和独立来源组，在已实现多种子汇总的基础上设计适当的区间估计；现有首批 239 条样本仍不能代表真实工程泛化性能。
3. 完整微调编码器、实现原始图引导注意力或更细粒度的 token—节点融合；当前仅是冻结序列编码加独立 GNN。
4. 增加缺陷类别头与更可靠的行定位，不将二分类告警当成已确认类型。
5. 改进别名、引用、堆和调用副作用覆盖；长函数分块与概率校准。
6. 在防止标签泄漏的前提下设计规则特征融合及对应消融；当前默认不使用规则特征。

### 验收

- 相同数据划分和配置可以复现实验结果。
- 模型告警复用统一 Finding 结构，并与规则告警区分。
- 分类与定位分别报告，不能只给总体准确率。

## 第三层 研究拓展 第13至16周

1. 先实现模板或掩码填充修复基线。
2. 生成多个统一差异候选，不直接修改原始工程。
3. 在临时副本中依次执行语法检查、编译、单元测试和回归测试。
4. 按验证状态、修改规模、告警消除和测试覆盖率排序。
5. 再尝试离散 token 或 AST 掩码扩散原型；若不收敛，保留基线闭环。
6. 统计 Patch Validity、编译通过率、测试通过率、正确修复率和 Top-k 修复成功率。

### 验收

- 每个候选都有差异文件与完整验证日志。
- 失败候选不会被静默丢弃。
- 演示材料能够清楚区分“候选已生成”“编译通过”“测试通过”和“正确修复”。
