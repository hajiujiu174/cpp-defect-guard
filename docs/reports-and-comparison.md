# P1-3 报告与版本对比

当前进度：2026-09-13 按以下范围完成。C++ Core 生成 HTML/JSON，CLI 和 Qt 共用历史快照、对比与导出接口。报告包含活动及已抑制问题、证据、解析覆盖、函数复杂度、配置和构建测试记录；两种文件均保留扫描 ID 与基线 ID。

## 使用

Qt 顶部点击“报告与对比”，选择报告版本和可选的较早基线，再填写新的报告目录。历史每页加载 50 个版本，可继续加载更早记录。历史读取和导出在后台执行；完成后显示两个文件的路径。任务执行期间等待其完成再关闭，不中断已经开始的文件输出。源码目录丢失时，已有数据库的历史报告仍可导出，源码导航和重新分析则需要恢复工程。

CLI 在仓库根目录运行，数据库须已经保存过项目扫描：

```powershell
$cli = '.\build\codeguard-analysis\codeguard-cli.exe'
$project = '.\samples\level3-demo'
$database = '.\artifacts\configured-demo.sqlite3'
& $cli scans $project --database $database --limit 50
# 分页用上一页最后一个 scan_id，边界不重复
& $cli scans $project --database $database --before 120 --limit 50
# 不带 --scan 导出最新扫描；可选 --baseline 指定较早版本
& $cli report $project --database $database --scan 120 --baseline 115 --output .\artifacts\review-120
```

扫描 ID 以实际输出为准。`scans` 支持 1—500 的分页大小；ID 为正整数，基线须更早且属于同一保存工程。项目参数采用数据库中保存的根目录，目录已不存在时仍可工作。`recent` 可查看已保存根目录。`report` 退出码 0 表示两个报告文件成功写入；分析状态仍在输出及报告内表示，`failed` 快照可以成功导出，它不因此变成分析通过。

`report.html` 不依赖网络、脚本、外部字体或源码文件，可单独复制给他人查看；详细配置、证据和日志通过折叠项展开。窄屏上的宽表可横向滚动。`report.json` 为 `CodeGuardReport` 版本 1，含 `snapshot`、可选 `baseline` 和 `comparison`，可由其他程序读取。HTML 显示 UTC 时间，JSON 保留原始时间字符串。

输出目录必须尚不存在、父目录已存在且位于源码树外；不会覆盖旧报告。写入出错时保留已经生成的文件，并明确报告失败，需另选新目录重试。源码、文件名、诊断和日志始终作为文本转义；截断造成的非法 UTF-8 在输出中替换为替代字符，JSON 中的控制字符会转义。

## 对比含义

先将活动和已抑制问题合并为观测集合。优先按规则、文件、函数标识、检测器、证据及行列匹配；只有同一函数内证据唯一且非 AST 占位时，才忽略行列移动。多处相同表达式不按任意顺序配对。不同模板实例保留自己的函数标识。

| 状态 | 含义 |
|---|---|
| `added` / `new_suppressed` | 本次新观测到，基线没有可靠匹配；不证明缺陷是本次引入 |
| `persistent` / `persistent_suppressed` | 相同规则证据继续存在，可能移动行列或改变级别 |
| `suppressed` / `reactivated` | 已观测问题转为抑制，或由抑制恢复活动；不是修复 |
| `file_removed` | 同样扫描范围下文件移出完整清单，可能删除、改名或路径类型变化；不计为修复 |
| `inventory_scope_changed` / `inventory_unknown` | 文件不在新清单中，但扫描范围变化或旧范围缺失 |
| `analysis_disabled` / `rule_disabled` | 本次没有执行分析或相应规则 |
| `parse_failed` / `coverage_lost` | 相关 TU 解析失败、编译命令缺失/被拒绝，或原覆盖来源消失 |
| `configuration_changed` / `analyzer_changed` | 实际编译命令指纹或分析器版本发生变化 |
| `configuration_unknown` / `provenance_unknown` / `coverage_unknown` | 历史证据不足，保留未知原因，不判修复 |
| `not_detected` | 相关 TU 在相同已记录分析条件下成功解析且未再检出，是待复核的修复候选 |

对于头文件中的旧问题，检查旧快照中覆盖该文件的全部 TU。如果某个原来源不再成功解析或不再覆盖该文件，就不会把旧问题当作修复候选。没有按单条 Issue 保存确切来源 TU，因此用全部覆盖来源作保守判断。文件改名、函数标识变化或证据编辑可能显示为旧项未检出和新项出现，不宣称完美跟踪问题身份。

`not_detected` 仍不能证明修复正确：当前尚未保存外部头文件内容、完整工具链文件和所有环境变量，也没有验证程序行为。源文件未变化却不再检出时，报告会明确要求检查依赖/环境变化。构建通过、测试通过及修复正确分别表示；CTest 未知数量保持 -1，跳过测试不算通过。

## 快照与兼容

SQLite schema 6 附加扫描范围、分析器版本、每 TU 编译命令指纹与 `unit_coverage`，在同一次扫描事务中保存。编译命令指纹来自实际选中命令的内容，能发现同一路径下 `compile_commands.json` 被修改；分析器版本结合规范化后的分析源码哈希及链接的 Clang 版本，避免文档提交或 CRLF 检出造成变化。扫描范围记录实际忽略目录及相对排除，包括 CLI 临时 `--ignore`。

只读支持 schema 1—6；可写打开旧库时附加事务迁移。旧快照缺少的新字段保持空值，报告据此显示未知，不追补成当前参数。规则配置仍为版本 2，兼容读取版本 1。旧二进制不能打开升级后的数据库。

历史快照不依赖当前源码。按扫描 ID 读取报告时，查询该批次的全部关联构建；旧 GUI/CLI 构建历史的最近 50 条限制不截断导出内容。构建 Git 提交是构建时记录，不伪装成扫描时已经记录的 Git 提交。完整报告入口载入构建日志；Core 接收仅摘要的调用方时会显式标注日志未载入。
