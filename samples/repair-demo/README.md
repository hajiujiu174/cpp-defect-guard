# 修复候选演示

本目录由项目内编写，故意保留 `is_zero` 条件赋值缺陷和 `format_label` 的无容量 API 提醒。原始版本的 `zero_classification` 测试预期失败；测试不会调用格式化函数，不执行其潜在越界路径。

先使用 CMake 生成编译数据库，再由 CodeGuard 扫描，选中 CG003 生成候选：

- 改为 `==`：符合本例明确写出的零值分类断言，可使副本测试通过。
- 加括号：保留赋值行为，CG003 不再提示，但副本测试仍失败。

两者用于说明“告警消失”和“行为测试通过”的区别；工具报告始终保留 `correctness=not_assessed`。本例的测试只验证已写出的分类要求，不代表所有真实工程的修复正确性。

CG001 可生成按 `label` 容量调用 `snprintf` 的候选，但它不会修复分类缺陷，因此单独验证该候选时测试仍会失败。格式化函数的截断、返回值和错误处理仍需审阅。

从“问题”表右键进入“生成修复候选 / 差异与副本验证”，或者使用 CLI `repair propose` / `repair validate`。所有候选及验证仅写到指定的源码外目录，原始示例文件保留。完整命令和范围见 [修复候选说明](../../docs/repair-candidates.md)。
